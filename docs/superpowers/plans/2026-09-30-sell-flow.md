# Sell Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let someone sell a tokenised stock they hold, in dollars, with the network fee sponsored — the exit the product has never had.

**Architecture:** Every server layer already takes a `side` and none has been passed `"sell"`. The work is four inversions in the money plumbing around the swap (charge position, rent target, where the fee comes out of, whether the minimum applies), one addition to the decision engine so a capped sell can explain itself, and the interface. The five-call order sequence — create, execute, sign, send, confirm — is unchanged.

**Tech Stack:** TypeScript (strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`), pnpm 10.33.2 workspaces + Turborepo, Vitest, Hono, `@solana/kit`, React 19 + Tailwind v4, Jupiter `/swap/v1`.

**Spec:** `docs/superpowers/specs/2026-09-30-sell-flow-design.md`

## Global Constraints

- `CreateOrderRequest.amount` stays **dollars for both sides**. The wire contract does not change.
- `max?: boolean` is the **only** new field on `CreateOrderRequest`.
- A sell **never** returns `offer_queue`. Out of tolerance with the market shut returns `execute` with a warning.
- `minOrderUsd` is a **buy-side rule**. It does not apply to a sell.
- A sell is refused only for: no route, no shares held, paused mint, stale reference, price impact too high, and proceeds below the network fee.
- **One issuer per sell**, capped at that wrapper's balance. Never split across wrappers.
- The charge goes **before** the swap on a buy and **after** it on a sell.
- Rent is owed on the **receiving** account: the stock mint on a buy, USDC on a sell.
- Sell presets are **25% · 50% · 75% · Sell all**.
- The Sell tab renders only when the user holds the stock.
- Conventional commits (`feat` / `fix` / `refactor` / `chore`); UI polish is `chore`.
- Never write the word "catalogue" — say stocks, supportedStocks or assets.
- `vitest` does not typecheck. Run `pnpm -r typecheck` **and** `pnpm -r test` before every commit.

## Facts established by reading the repo (do not re-derive)

- `deps.chain` (`deps.ts:165`) is the **raw** `ChainReader`. Only `buildReconcileDeps` (`:211`) wraps it with `withPledged`. So `tokenBalances` in the pricing path returns **wallet-only** balances, and pledged tokens are already excluded. The server cannot oversell pledged shares; only the interface has to explain the gap.
- `Quote.inAmount` already carries the token amount a sell was quoted for (`jupiter/lite.ts:93` falls back to the request amount when Jupiter omits it). **No new field on `Candidate` is needed** — the spec's §3 anticipated one; the quote already has it.
- `ExecuteDecision` already has a `warning` field, and `decide.ts:204` already writes the sell copy.
- `planFill` reads the **net** USDC delta, so a sponsored sell records proceeds net of the fee. That is correct and symmetric with a buy recording gross spend. No change; Task 7 adds a test.

### Task 1: `filledShares` on every priced candidate

A sell capped at a wrapper's balance trades fewer shares than were asked for, and the ticket has to say so. The quote already knows: tokens are `outAmount` on a buy and `inAmount` on a sell, and shares are tokens times the multiplier.

This touches the buy path, so the buy path must be provably unchanged.

**Files:**

- Modify: `packages/core/src/execution/types.ts:100-122` (the `PricedCandidate` interface)
- Modify: `packages/core/src/execution/decide.ts:25-40` (the `base` object inside `priceCandidate`)

- [ ] **Step 3: Write the module**

Create `services/api/src/orders/sellable.ts`:

```ts
import { D, type Decimal } from "@mercury/core";
import type { TokenBalance } from "@mercury/chain";

/**
 * How many tokens of each wrapper a sell can actually consume.
 *
 * A sell is asked for in shares, and a share is not a token: every wrapper
 * carries its own multiplier, so the same two shares are a different number of
 * tokens in each. And no wrapper can sell more than the wallet holds of it.
 *
 * Pledged stock never appears here, and that is not an oversight. `deps.chain`
 * is the raw reader — only the reconciler wraps it with `withPledged`, so what
 * Kamino holds as collateral is simply not in these balances. The books count
 * it as owned; the wallet cannot spend it.
 *
 * Pure. No chain, no clock.
 */

export interface SellableWrapper {
  readonly mint: string;
  readonly decimals: number;
  /** Shares of the underlying that one token represents. Always >= 1. */
  readonly multiplier: Decimal;
}

export interface SellableAmount {
  readonly mint: string;
  /** Whole tokens to sell. Never more than the wallet holds. */
  readonly tokens: Decimal;
  /** True when the balance, not the request, decided the amount. */
  readonly capped: boolean;
}

/** `shares` of null means everything: what "Sell all" asks for. */
export const sellableAmounts = (
  wrappers: readonly SellableWrapper[],
  balances: readonly TokenBalance[],
  shares: Decimal | null,
): readonly SellableAmount[] => {
  const byMint = new Map(balances.map((b) => [b.mint, b]));

  return wrappers.flatMap((w) => {
    const balance = byMint.get(w.mint);
    if (balance === undefined || balance.rawAmount <= 0n) return [];
    const held = D(balance.rawAmount.toString()).div(D(10).pow(balance.decimals));

    if (shares === null) return [{ mint: w.mint, tokens: held, capped: false }];

    /*
     * Down, always. Rounding a share count up asks the swap for tokens the
     * wallet does not have, and the transaction fails on chain after the user
     * has already signed it.
     */
    const wanted = shares.div(w.multiplier).toDecimalPlaces(w.decimals, D.ROUND_DOWN);
    const capped = wanted.gt(held);
    return [{ mint: w.mint, tokens: capped ? held : wanted, capped }];
  });
};
```
